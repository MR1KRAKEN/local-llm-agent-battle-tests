## Результат коротко

**Вердикт: ❌ для кода в кванте Q1_0 непригодна.** Ни одной успешной сборки, затем дегенерация.
Это ожидаемо: модель по назначению вижн-модель, а Q1_0 — экстремальное квантование (около 1 бита на вес).
По решению владельца стенда из этапа доработки модель исключена.

## Что именно сломалось

**Ошибки компилятора (обе сборки):** `CS0103` (имя не существует в контексте), `CS0117` (у типа нет
члена), `CS0123` (нет перегрузки под делегат), `CS0246` (тип не найден), `CS1061` (нет такого члена),
`CS1503` (нельзя преобразовать аргумент), `CS1729` (у типа нет конструктора с такими аргументами),
плюс предупреждение `CS8632` (аннотация nullability без `#nullable`).

**Дегенерация.** После двух неудачных сборок модель начала ответ, который не заканчивался:
в логе llama.cpp счётчик сгенерированных токенов дошёл до **15 574** при `defaultMaxTokens: 8192`,
около 10 минут подряд на ~53 tok/s. Файлы при этом не менялись. Оркестратор прервал прогон вручную —
сама модель из цикла не вышла.

Это важный практический вывод для локальных запусков: **нужен жёсткий лимит токенов на шаг**,
иначе один ответ может съесть всю сессию.

## Что стоит знать

- Стиль ошибок тот же, что у остальных моделей малого класса: выдуманные члены API, потерянные `using`,
  несуществующие конструкторы. Отличие в том, что исправлять их модель не пыталась.
- Квант Q1_0 даёт заметную деградацию даже на уровне связности ответа: медленный TTFT (7.74 с),
  длинные ответы без прогресса.
- Для вижн-задач (у модели есть `mmproj`) эти тесты ничего не говорят — они про генерацию кода.

## Воспроизведение

```
1. llama-server -m Bonsai-27B-Q1_0.gguf --mmproj mmproj-Bonsai-27B-BF16.gguf \
     --host 127.0.0.1 --port 8090 --alias bonsai-27b-64k -c 65536 -fa on -ctk q8_0 -ctv q8_0 \
     --jinja -np 1 --reasoning-format deepseek --reasoning-budget 0
2. Задача: WinForms-калькулятор (.NET 8) + publish.
3. Обязательно: внешний лимит токенов на шаг — иначе дегенерация не остановится сама.
```
