# Заметки по оркестрации: параллелизм, роли и повторяемость

**Языки:** Русский (этот файл) · [English](../orchestration-notes.md)

Замеры сделаны на стенде проекта при запуске локальных моделей субагентами DSH. Они про **харнесс**, а не
про конкретную модель, поэтому вынесены отдельно от отчётов по моделям.

Стенд: AMD Ryzen 7 9800X3D, 64 ГБ DDR5, **NVIDIA RTX 4070 Ti 12 ГБ**, Windows 11, llama.cpp CUDA `b12248`.

## 1. Сколько агентов влезает на один сервер

llama.cpp обслуживает несколько запросов сразу при `-np N`. Он их батчит: суммарная пропускная способность
растёт, а каждый отдельный запрос замедляется. Замер на Bonsai-27B (Q1_0, 3.5 ГиБ — достаточно мала, чтобы
форма кривой была видна отчётливо), по 220 сгенерированных токенов на запрос:

| Агентов одновременно | На агента | Суммарно | % от одного | VRAM |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 75.8 tok/s | 75.8 tok/s | 100% | 8.9 ГиБ |
| 2 | 63.4 tok/s | 126.6 tok/s | 164% | — |
| 4 | 42.5 tok/s | 177.1 tok/s | 220% | 8.9 ГиБ |
| 8 | 27.4 tok/s | 219.2 tok/s | 289% | 9.4 ГиБ |
| 16 | 18.2 tok/s | **289.9 tok/s** | **383%** | 10.7 ГиБ |

Та же форма у модели побольше — Qwen3.5-9B, `-np 4`, `-c 131072`:

| Агентов одновременно | На агента | Суммарно |
| ---: | ---: | ---: |
| 1 | 67.5 tok/s | 67.5 tok/s |
| 4 | 58.4 tok/s | **233.3 tok/s** |

А при `-np 2` два агента в момент одновременной работы выдавали по **61–64 tok/s**.

**Практический вывод.** Рабочая точка — четыре агента: каждый работает примерно на скорости одиночной
крупной модели, но таких агентов четыре. Восемь по 27 tok/s — уже вяло для агентской работы; шестнадцать
имеет смысл только для пакетных задач, где медленный прогресс допустим.

## 2. Ловушка: контекст делится между слотами

`-c` задаёт **общий** контекст сервера, и он распределяется по слотам: контекст на слот = `-c / np`.
Только системный промт DSH занимает около **12 278 токенов**. Поэтому конфигурация `-c 32768 -np 4` даёт
по 8 192 токена на слот, и каждый запрос падает сразу:

```
400: {"message":"request (12278 tokens) exceeds the available context size (8192 tokens),
      try increasing it"}
```

Рабочая конфигурация для четырёх агентов: `-c 131072 -np 4` — по 32К на слот, этого хватает на промт,
схемы инструментов и рабочий контекст.

## 3. Разделение ролей между агентами

Конвейер проверен на Qwen3.5-9B (`-np 4`, по 32К на слот): исследователь, три параллельных исполнителя,
проверяющий.

| Роль | Что делала | Итог |
| :--- | :--- | :--- |
| Исследователь | `web_fetch` статьи, записал `research.md` (2.4 КБ) | справился со второй попытки — в первый раз прочитал страницу и не создал файл |
| Исполнитель Python | `calc.py` | **8/8** |
| Исполнитель JS | `calc.js` | **8/8** |
| Исполнитель C | `calc.c` + `calc.exe` | **0/8** — `fgets` без цикла, читает одну строку |
| Проверяющий | прогнал все три, записал `review.md` | **точно**: 8/8, 0/8, 8/8 — совпало с независимой проверкой оркестратора |

Параллелизм подтверждён логом сервера: слоты 0, 1 и 2 одновременно обрабатывали запросы, каждый на
30–35 tok/s против 67.5 в одиночном режиме.

**Наблюдения:**

- Разделение ролей работает. Исследователь действительно сходил в интернет (один из двух таких случаев за
  весь проект), а проверяющий корректно сообщил о единственном провале, ничего не выдумав.
- Отдельный исследователь для простой задачи малополезен: его выжимка была общими знаниями, которые у
  модели уже есть. Польза появляется там, где нужны факты, которых модели не хватает.
- Параллельные исполнители пишут код хуже, чем одиночные. У JS-агента в файле оказалось двойное объявление
  `const tokens` — файл вообще не парсился, тогда как в одиночном прогоне та же модель дала 8/8.

## 4. Повторяемость: одна задача, один промт, четыре прогона

Qwen3.5-9B, четыре независимых прогона **идентичного** промта: консольный калькулятор на Python с проверкой
на тех же восьми выражениях. Проверял оркестратор, а не модель.

| Прогон | Результат | Что сломалось |
| :--- | :--- | :--- |
| run-1 | **8/8** | — |
| run-2 | **5/8** | `RecursionError: maximum recursion depth exceeded` на `(2+3)*4`; до этого `0.1+0.2` напечатал `0.30000000000000004` |
| run-3 | **7/8** | `-4+10` → `-14`: унарный минус захватил всё выражение |
| run-4 | **8/8** | — |

**Среднее — 7.0 из 8; полностью корректных — 2 из 4 (50%).**

Два вывода:

1. **Меняется не только результат, но и способ поломки.** На одном задании проявились три разных класса
   дефектов: краш рекурсии, форматирование float и приоритет унарного минуса. Знание «модель это умеет»
   ничего не говорит о том, *как* она сломается в следующий раз.
2. **Самоотчёт ненадёжен.** В 2 из 4 прогонов модель заявила 8/8 при фактически худшем результате
   (run-2 отрапортовал успех с падающей программой). Вывод агента обязательно надо проверять запуском.

## 5. Стоимость: токены на задачу не менее важны, чем tok/s

Быстрая модель может позволить себе зацикливаться, и счёт приходит в токенах. Наблюдения на том же стенде:

| Прогон | Потрачено токенов | Время | Результат |
| :--- | ---: | ---: | :--- |
| Bonsai-27B, консоль на Rust | **1.4 млн** | 6 м 45 с | exe собрался, но падает на первом вводе — 0/8 |
| qwen3:30b, консоль на Java | 389 тыс. | 12 м 10 с | 6/8, позже исправлено до 8/8 |
| qwen3:30b, Rust повторно | 129 тыс. | 5 м 49 с | 8/8 |
| flint-24B, бюджет рассуждений 32К | 44.6 тыс. | 10 м 17 с | ноль вызовов инструментов |

Модель на 70 tok/s, которая думает по кругу, обходится дороже, чем медленная модель, которая действует.
Высокий `tok/s` сам по себе — обманчивый показатель для агентской работы.

## Воспроизведение настроек харнесса

```powershell
# четыре агента, по 32К контекста каждому
llama-server -m model.gguf --host 127.0.0.1 --port 8090 --alias model-alias `
  -c 131072 -fa on -ctk q8_0 -ctv q8_0 --jinja -np 4 --no-webui
```

Замеры и текст — **DeepSeek-V4.1-Flash** (оркестратор DSH); код моделей он не писал и не исправлял.
